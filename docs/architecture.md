# Архитектура пилота SPROS

## Продукт и сценарии

Житель: карта → запрос → поддержка/сумма намерения → сохранённое участие в профиле. Если подходящего запроса нет: место → категория и описание → проверка похожих запросов → сумма намерения → публикация. Присоединение к похожему запросу сохраняет один голос вместо создания новой точки.

Предприниматель: карта возможностей → категория, район, число голосов, желаемый чек, сумма намерений, радиус → спрос → концепция. Альтернативно самостоятельная идея бизнеса. Жители сравнивают концепции и выбирают одну; выбор можно изменить. Заявка на предзаказ/сертификат/инвестиционное обсуждение — отдельный тип интереса, без денежной операции.

Модератор: жалоба → проверка конкретного нарушения → объяснённое решение → журнал. Жалоба не меняет статус запроса. `review` остаётся видимым. Скрытые записи доступны автору и модератору, автор может апеллировать. Апелляция может быть удовлетворена или отклонена с объяснением. Необычные идеи, критика и непопулярность не фильтруются автоматически.

## Модули и данные

| Слой              | Ответственность                                                                 |
| ----------------- | ------------------------------------------------------------------------------- |
| React-компоненты  | Доступные формы, состояние экрана, карта и карточки                             |
| Domain            | Предметные типы, геометрия, категории, валидация, разрешённые переходы статусов |
| API               | Идентификация, проверка входных данных, права и команды                         |
| Server/repository | Подготовленные SQL-запросы и формирование моделей чтения                        |
| D1 + Drizzle      | Долговечные записи и миграции схемы                                             |
| R2                | Байты изображений; владелец и MIME находятся в D1                               |

Таблицы: `users`, `requests`, `supports`, `offers`, `choices`, `interests`, `reports`, `appeals`, `moderation_events`, `action_limits`, `media`.

`supports` имеет составной первичный ключ `(request_id,user_id)`. Повторное действие обновляет сумму намерения, не увеличивая число голосов. `choices` имеет ключ `(user_id,request_id)`, поэтому невозможно выбрать две концепции одного спроса. Финансовая готовность хранится отдельно от выбора концепции и интереса к сертификату.

При слиянии реальные голоса переносятся транзакционной D1 batch-операцией. Пересечение аккаунтов дедуплицируется, из двух намерений берётся максимум. Источник получает `merged` с целевым ID. Демонстрационные исходные счётчики не суммируются при слиянии: у них нет индивидуальных записей для проверки пересечений.

## Идентификация и злоупотребления

Идентичность принимается только из проверенных платформой заголовков. Публичный клиент не передаёт доверенный `userId` в теле команды. Прямой доступ к Worker вне проверяющего dispatcher запрещён при самостоятельном размещении; при переносе заменить идентификацию серверной сессией выбранного провайдера.

- Один голос на аккаунт гарантируется БД.
- До 3 запросов и 3 концепций за сутки, до 10 загрузок за сутки, отдельные часовые лимиты действий.
- Лимит увеличивается атомарным SQL, хранится с временем окна и применяется на сервере.
- Публикация, поддержка, жалобы, заявки, загрузки и профиль требуют входа.
- Апелляции требуют совпадения с автором; решения требуют явного списка модераторов.
- Формы ограничены по длине и диапазонам, SQL параметризован. Подсказки карты используют textContent.
- Изображения до 5 МБ: JPEG/PNG/WebP по сигнатуре; SVG не принимается. Неопубликованные файлы видит владелец, чужое изображение нельзя присоединить к предложению.
- Телефон и проживание пока не подтверждаются; поля для проверенных сигналов зарезервированы, клиент не может их менять.

Текущие лимиты — базовая защита от массовых действий, не полноценный антифрод. До роста: IP/session burst signals, журнал риск-событий, подтверждение номера, защита регистрации, ручные проверки подозрительных групп, тест ложных срабатываний. Не собирать точный домашний адрес или паспорт без необходимости. Взвешивание голосов пока не используется.

## Карта и подсчёт

Координаты WGS84 не привязаны к поставщику карты. `map-config.ts` задаёт слой. Текущий слой — OpenStreetMap, с видимой атрибуцией; без предзагрузки и офлайн-скачивания. Для трафика полевого пилота проверить доступность и условия выбранного поставщика, при необходимости заменить слой.

- [Leaflet Quick Start](https://leafletjs.com/examples/quick-start/)
- [OSM Tile Usage Policy](https://operations.osmfoundation.org/policies/tiles/)

Группировка — сетка экранных координат Web Mercator, размер зависит от масштаба. Близкие совпадающие точки раскрываются списком, чтобы запросы не становились недоступными. Число на кластере спроса — сумма голосов, не уникальные люди: один человек мог поддержать несколько запросов.

Горячие зоны вычисляются из голосов запросов; сейчас это демонстрационная интенсивность, не статистическая модель района. Список ограничен 500 записями на пилот. Для большого города нужны серверный bbox, пагинация, пространственный индекс и серверная кластеризация.

Сумма намерений не является выручкой. Бакеты «до 1/5/15 тысяч» — выбранные верхние границы, «50 тысяч и больше» хранится как 50 000 с известной семантикой категории. Сумма — приблизительный сигнал; нельзя использовать её как прогноз гарантированных предзаказов.

## Переход к PostgreSQL / Supabase

1. Сохранить публичные TypeScript-модели и контракт API.
2. Перевести определения Drizzle SQLite на pg-core, сохранив уникальные ключи и внешние связи.
3. Заменить `database()` и SQL-исполнение на PostgreSQL через HTTP-совместимый клиент; batch заменить транзакциями. В Workers нельзя рассчитывать на обычный TCP-клиент.
4. Заменить `?` на параметризацию выбранного драйвера и пересмотреть SQLite-специфичные операции.
5. Вынести географию в PostGIS: nearest-neighbor и индексы. Не менять координаты интерфейса.
6. Заменить только модуль идентификации. Не считать запись района подтверждённым проживанием.
7. Оставить интеграционные сценарии как регрессионный контракт при смене адаптера.

## Будущая монетизация

Комиссии и платежи добавляются отдельными `orders/payments/refunds`, с идемпотентностью и журналом платёжных событий. Поддержка и intent не превращаются в платёж задним числом. Инвестиционный модуль — отдельная интеграция с выбранным партнёром.

Платное продвижение потребует явного отличия рекламы от органического рейтинга. Бизнес-подписки — слой прав/тарифов вокруг расширенных фильтров и агрегатов. Аналитика для сетей и девелоперов — агрегированные данные с порогами приватности. Пилот не содержит платных заглушек в пользовательских сценариях.

## Проверка и ограничения запуска

TypeScript и production-сборка. Изолированные интеграционные проверки собранного Worker с D1/R2. Отдельные предметные проверки радиуса, дубликатов, кластеров и модерации. Проверка в настоящем браузере и WebMCP-контексте в этой сессии не выполнялась; перед полевым запуском нужна проверка на телефонах жителей.

Первая публикация закрытая. Для внешних участников владелец задаёт аудиторию через настройки сайта. Модератор по умолчанию не назначен; явный список аккаунтов задаётся через секрет окружения.
